## 1. 프로젝트 개요와 범위

### 1.1 목적

집 근처 정류소 한 곳의 실시간 버스 도착 정보를 제공하고, 큰 글씨·음성·빛·소리를 함께 사용하여 정보를 쉽게 확인하도록 한다. 교통약자를 배려하면서 일반 이용자도 관심 버스 선택과 휴대폰 페이지를 편리하게 사용할 수 있도록 한다.

### 1.2 해결하려는 문제

- 작은 글씨로 표시된 버스 정보를 읽기 어려울 수 있다.
- 여러 노선 중 자신이 탈 버스의 정보를 계속 확인해야 한다.
- 화면을 보고 있지 않으면 도착 임박 상태를 놓칠 수 있다.
- 색상만으로 정보를 표현하면 상태를 구분하기 어려울 수 있다.
- 정류소 안내판 가까이에 가지 않고도 휴대폰으로 정보를 확인할 필요가 있다.

### 1.3 개발 범위

| 구분 | 내용 |
| --- | --- |
| 정류소 | 실제 정류소 한 곳, 한 방향을 고정한다. 반대편 정류소는 별도 대상으로 취급한다. |
| 표시 노선 | 해당 정류소의 경유 노선을 대상으로 한다. 도착 정보가 없는 노선도 가능한 경우 목록에 유지한다. |
| 공용 관심 노선 | 초기 버전은 한 번에 1개만 선택한다는 추천안이다. |
| 모바일 관심 노선 | 각 접속자의 세션별 1개 선택을 추천한다. 공용 선택과 분리한다. |
| 실시간 정보 | 외부 API가 제공하는 도착 예측 정보를 주기적으로 조회한다. 실제 도착을 센서로 확인하는 기능은 포함하지 않는다. |
| 장치 | UNO R4 WiFi, 버튼, 네오픽셀 또는 RGB LED, 부저 |
| 화면 | PC 공용 안내 화면과 모바일 브라우저 화면 |
| 음성 | 초기 버전은 PC의 한국어 음성 합성과 스피커를 사용한다. |
| 통신 | 첫 버전 USB 시리얼, 이후 필요하면 WiFi로 확장한다. |

### 1.4 초기 범위에서 제외하는 기능

자동 차양, 팬, 미세먼지 측정, 얼굴 인식, 인원 계수, 자동 경로 검색, 운수회사 전송, 실제 버스 기사에게 승차 의사 전달은 별도 확장 항목이다. 휴대폰 페이지를 닫아도 동작하는 푸시 알림은 기본 범위에 포함하지 않는다.

### 1.5 성공 기준

- 지정한 정류소와 방향의 도착 정보가 표시된다.
- 선택 노선이 명확하게 표시되고 물리 버튼으로 조작할 수 있다.
- 최신 정보에 근거한 도착 임박 표시와 중복 방지 알림이 작동한다.
- 정보 미제공·통신 실패가 정상 데이터와 구별된다.
- 저상버스 여부를 차량별로 표시하며, 알 수 없는 경우 추측하지 않는다.
- 간편 안내 요청에 큰 글씨와 음성으로 응답한다.
- 휴대폰 선택이 공용 선택 또는 다른 이용자의 선택을 변경하지 않는다.

## 3. 권장 시스템 구성

### 3.1 구성 요소별 책임

| 구성 요소 | 책임 | 소유하는 상태 |
| --- | --- | --- |
| Python 공통 서비스 | 외부 API 조회, 정규화, 캐시, 공용 관심 노선, 알림 판단, 장치 연결 | 버스 스냅샷, 공용 선택, 알림 기록, 장치 상태 |
| Streamlit 공용 화면 | 정보 표시, 공용 화면 조작 | 화면 옵션; 공용 선택의 원본은 서비스가 관리 |
| Streamlit 모바일 화면 | 정류소 정보 표시, 개인 노선 선택 | 개인 선택·큰 글씨 등 세션 상태 |
| Arduino | 버튼 입력 감지, LED·부저 출력, 연결 확인 | 핀 상태, 최근 명령, 이벤트 순번 |
| PC 음성 모듈 | 안내 문장 재생 | 음성 작업 큐와 재생 상태 |
| OpenAPI 제공 기관 | 원본 버스 도착 예측 제공 | 외부 정보 |

### 3.2 권장 구현안

Python 공통 서비스를 하나의 프로세스로 실행하고, Streamlit 화면은 공통 서비스의 데이터를 읽도록 한다. 공통 서비스에 간단한 FastAPI 인터페이스를 두는 방식을 추천한다. UI 세션이 늘어나도 아두이노와 외부 API를 관리하는 주체가 하나여서 중복 알림과 시리얼 포트 충돌을 줄이기 쉽다.

이 구조는 이전에 제안한 Streamlit 단독 방식보다 파일이 조금 늘지만, 공용 버튼과 여러 휴대폰을 함께 지원하는 최종 목표에 적합하다. 최초 API 조회 실험은 짧은 Python 스크립트로 해도 된다.

### 3.3 중요한 경계

- 아두이노는 외부 버스 API를 직접 해석하지 않는다.
- 시리얼 포트는 Python 서비스 한 곳만 연다.
- 모바일 페이지는 공용 LED·부저·PC 스피커를 직접 제어하지 않는다.
- 모바일 음성은 휴대폰 브라우저에서 재생해야 한다. 서버의 음성 합성 호출은 서버 PC에서 소리가 나는 것이므로 대체할 수 없다.
- Streamlit 화면 갱신 또는 브라우저 새로고침이 도착 알림의 발생 조건이 되어서는 안 된다.
- USB와 WiFi 장치 연결을 동시에 활성화하지 않는다.

### 3.4 USB 이후 WiFi 확장

기능 완성 후 통신 어댑터만 교체할 수 있도록 장치 통신 코드를 분리한다. WiFi 확장 시 Arduino가 Python 서비스로 버튼 이벤트를 보내고 명령을 조회하는 HTTP 방식 또는 MQTT 중 하나를 선택한다. 네트워크 방식·재전송·접근 제어는 별도 확장 설계로 작성한다. UNO R4 WiFi를 사용하더라도 첫 버전에 WiFi 통신이 필수인 것은 아니다.

### 4.1 기본 부품

| 부품 | 수량 | 용도 | 비고 |
| --- | --- | --- | --- |
| UNO R4 WiFi | 1 | 입력·출력 제어 | 기존 보드 활용 |
| 푸시버튼 | 3 | 다음 노선, 선택/해제, 안내 요청 | 안내 요청은 큰 버튼 권장 |

| PC/노트북 | 1 | Python 서비스와 안내 화면 | 상시 동작 필요 |

| 데이터 통신 USB 케이블 | 1 | PC–Arduino 연결 | 충전 전용 케이블 제외 |
| 모형·라벨 | 필요량 | 안내판과 버튼 배치 | QR와 기능 설명 부착 |

### 4.2 핀 배치 추천안

| 핀 | 연결 대상 | 설정안 |
| --- | --- | --- |
| D2 | 다음 노선 버튼 | INPUT_PULLUP, 눌림 LOW |
| D3 | 선택/해제 버튼 | INPUT_PULLUP, 눌림 LOW |
| D4 | 안내 요청 버튼 | INPUT_PULLUP, 눌림 LOW |
| D6 | 네오픽셀 데이터 입력 | 라이브러리 출력 |
| D8 | 부저 제어 | 부저 유형·전류에 따라 직접 또는 구동 회로 |
| GND | 버튼·LED·부저 공통 기준 | 외부 전원 사용 시 공통 접지 |

핀 배치는 제안이며 실제 부품의 회로·라이브러리와 대조한다. 버튼은 내부 풀업 기준으로 핀과 GND 사이에 연결한다. LED 데이터 저항·전원 안정화 부품·전원 전류는 모듈 설명서를 확인한다. 네오픽셀 전류는 밝기·색상에 따라 달라지므로 최대 밝기로 시작하지 않는다. 부저 역시 보드 핀의 허용 전류를 넘는 부품은 구동 회로가 필요하다.

### 4.3 장치 동작 기준

- 전원 직후 부저는 무음, LED는 준비/연결 대기 상태로 시작한다.
- 버튼 입력은 약 30~50ms 디바운스를 초기 실험값으로 적용한다.
- 길게 누른 입력을 여러 번으로 처리할지 여부는 추후 정한다. 최초 버전은 눌림 1회당 이벤트 1회를 추천한다.
- 부저와 LED 효과는 다른 버튼·통신 처리를 멈추지 않도록 구성한다.
- 연결이 끊기면 이전 도착 임박 표시가 계속 최신 정보처럼 남지 않도록 시간 제한을 둔다.

| 항목 | 추천안 | 확인할 사항 |
| --- | --- | --- |
| Python | 3.11 또는 3.12 가상환경 | 사용할 라이브러리 호환성 확인 |
| API 요청 | requests | 타임아웃, JSON/XML 응답 처리 |

| 음성 | OS 한국어 TTS를 지원하는 Python 도구 | 한국어 음성 설치·실제 재생 확인 |

패키지 버전은 설치 후 정상 동작한 버전으로 고정한다. 본 문서의 버전 선택은 개발 추천안이며 최신 패키지의 호환성 보증이 아니다.

서비스는 예를 들어 127.0.0.1:8000, UI는 8501 포트를 사용할 수 있다. 휴대폰 같은 WiFi 접속에는 UI의 네트워크 바인딩, PC 방화벽, 휴대폰과 PC의 통신 가능 여부를 확인한다. 0.0.0.0은 서버의 수신 설정이며 QR에 넣을 접속 주소가 아니다. QR에는 PC의 실제 로컬 IP 또는 배포된 도메인을 넣는다.

## 6. OpenAPI 연동 설계

### 6.1 선택 기준

대상 정류소가 경기도라면 경기버스정보 도착 API를 우선 검토한다. 다른 지역이거나 제공 범위가 맞지 않으면 TAGO 또는 해당 지역 API를 검토한다. 정류소를 지정하기 전까지 제공 기관은 확정하지 않는다.

### 6.2 시작 전 확보할 정보

| 항목 | 기록란 | 확인 방법 |
| --- | --- | --- |
| 정류소명 | 미정 | 실제 표지·공식 조회 |
| 방향 | 미정 | 다음 정류소 또는 종점 확인 |
| 표지판 번호 | 미정 | 현장 번호 기록 |
| API 정류소 ID | 미정 | 공식 정류소 조회로 확인 |
| 도시코드 | 필요 시 미정 | 선택 API 확인 |
| 대표 시연 노선 | 미정 | 실제 도착 정보 제공 확인 |
| API 인증키 | 환경변수 저장 | 활용신청·승인 확인 |
| 호출 한도 | 미정 | 승인 계정의 실제 한도 |
| 이용 조건 | 미정 | 출처 표시·재배포 조건 확인 |

정류소 표지판 번호와 API 내부 ID는 동일하다고 가정하지 않는다. 반대 방향 정류소와 혼동하지 않도록 방향을 화면에 표시한다.

### 6.3 공식 문서에서 확인한 핵심 항목

경기도 v2 도착 API 문서에는 stationId, routeId, routeName, predictTime1/2(분), predictTimeSec1/2(초), locationNo1/2, lowPlate1/2, vehId1/2 항목이 있다. 저상버스 구분은 lowPlate 값 1이며, 다른 특수 차량도 있으므로 단순한 참/거짓 변환 전에 유형을 해석한다. 실제 노선의 누락값·초 단위 값 제공 여부는 샘플 응답으로 검증한다.

- 공식 매뉴얼: https://www.gbis.go.kr/gbis2014/publicService.action?cmd=mBusArrivalStation
- TAGO 도착정보: https://www.data.go.kr/data/15098530/openapi.do
- 확인일: 2026-10-04

### 6.4 정규화 원칙

외부 API 필드명을 화면·알림 로직에서 직접 사용하지 않는다. API 어댑터가 내부 모델로 바꾼다. 시간은 내부에서 초 단위로 통일하고, 화면은 원본 정밀도에 맞게 표시한다. 분 값만 있으면 60을 곱해 비교할 수 있으나 초 단위로 정밀하게 관측한 값처럼 표시하지 않는다.

- 빈 문자열·미제공·문서상 미상값은 null로 정리한다.
- 0과 null을 구분한다. 0의 의미는 선택 API의 상태와 함께 확인한다.
- 음수값을 임의로 0초로 바꾸어 임박 알림을 만들지 않는다.
- HTTP 성공과 API 업무 결과 성공을 각각 확인한다.
- 항목이 한 개·여러 개·없음인 응답을 모두 처리한다.
- 노선 목록과 도착 목록을 분리한다. 도착 목록에 없다고 노선이 없어졌다고 단정하지 않는다.
- API 목록에 나타나지 않는 노선을 ‘운행 종료’로 단정하지 않는다.

### 6.5 호출과 캐시 기준

초기 추천 갱신 주기는 30초, 최신성 제한은 90초다. 이는 정책이 아니라 실험값이다. 30초 간격으로 하루 종일 실행하면 약 2,880회 조회가 발생하며, 메타데이터·재시도 호출은 추가된다. 실제 승인 한도에 맞추어 운영 시간과 주기를 조정한다.

최근 성공 결과와 최근 시도 결과를 별도로 보관한다. 요청 실패가 발생하면 실패 표시를 즉시 보여주며, 기존 값은 마지막 성공 시간과 함께 참고 정보로 유지할 수 있다. 새 소리 알림은 성공·최신 상태의 데이터에 한정한다. 브라우저마다 외부 API를 호출하지 않는다.

## 7. 내부 데이터 구조

### 7.1 StationConfig — 고정 정류소

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| provider | str | gbis/tago 등 |
| station_id | str | API 정류소 ID |
| station_name | str | 표시 이름 |
| direction_label | str | 방향 설명 |
| city_code | str 또는 null | 필요한 제공 기관에서만 사용 |
| public_station_number | str 또는 null | 현장 번호 |

### 7.2 Route — 노선 기본 정보

route_id(str), route_name(str), destination(str 또는 null), display_order(int), enabled(bool)를 가진다. 식별은 노선 ID로 하고 노선 번호는 표시용으로 사용한다.

### 7.3 Arrival — 도착 대상 차량

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| route_id | str | 노선 ID |
| vehicle_id | str 또는 null | 원본이 제공하는 차량 ID |
| arrival_rank | int | 첫 번째·두 번째 도착 등 |
| eta_seconds | int 또는 null | 예상 시간 |
| eta_precision | str | seconds/minutes/unknown |
| remaining_stops | int 또는 null | 남은 정류장 |
| vehicle_type | str | low_floor/standard/other/unknown |
| source_status | str 또는 null | 원본 상태값 |
| observed_at | 시간 | 서버에서 정상 수신한 시점 |

### 7.4 ArrivalSnapshot — 조회 결과

station_id, routes, arrivals, fetched_at, last_success_at, fetch_status, error_code, error_message, snapshot_version을 가진다. 조회 상태는 OK/EMPTY/ERROR/STALE로 구분한다. EMPTY는 정상 조회에 도착 결과가 없는 상황이며 ERROR와 구별한다.

### 7.5 PublicSelection — 공용 선택

candidate_route_id, selected_route_id, alert_enabled, large_text_enabled, selection_revision을 가진다. 후보와 확정 선택을 구분할지는 후속 사용자 흐름 설계에서 확정한다. 최초 구현은 한 개 선택을 추천한다.

### 7.6 PersonalSelection — 모바일 개인 선택

session_id, selected_route_id, large_text_enabled, browser_audio_enabled를 가진다. 초기에는 로그인 없이 세션 단위로 보관하며 서버 재시작·브라우저 종료 후 복원이 보장되지 않는다. 영구 즐겨찾기는 추후 기능이다.

### 7.7 AlertRecord — 중복 방지 기록

station_id, route_id, arrival_identity, lifecycle_id, notified_at, expires_at를 가진다. 차량 ID는 다른 운행에서도 재사용되므로 차량 ID만 영구 저장하여 알림을 막지 않는다. station_id + route_id + vehicle_id + 도착 주기 식별자를 추천한다. 정확한 주기 종료 기준은 샘플 데이터와 후속 처리 흐름 설계에서 확정한다.

### 7.8 내부 모델 예시 — 모의 데이터

```json
{
  "station_id": "DEMO_STATION",
  "station_name": "시연 정류소",
  "direction_label": "시청 방향",
  "fetch_status": "OK",
  "fetched_at": "2026-10-04T17:00:00+09:00",
  "snapshot_version": 7,
  "arrivals": [
    {
      "route_id": "DEMO_ROUTE_12",
      "vehicle_id": "DEMO_BUS_A",
      "arrival_rank": 1,
      "eta_seconds": 110,
      "eta_precision": "seconds",
      "remaining_stops": 2,
      "vehicle_type": "low_floor"
    }
  ]
}
```

위 JSON은 내부 설계 예시이며 실제 API 응답이 아니다.

## 8. 기능별 상세 명세

### FR-01~03: 실시간 정보 제공

- 입력: 정류소 설정, 외부 API 응답.
- 출력: 노선별 도착 정보, 갱신 시간, 정상/오류 상태.
- 규칙: 예상 시간이 없으면 ‘도착 정보 없음’; 조회 실패이면 ‘정보 갱신 실패’; 오래된 정보이면 ‘마지막 정보 — 갱신 지연’처럼 구별한다.
- 정렬: 초기에는 고정 노선 순서 추천. 버튼으로 탐색 중 API 갱신으로 항목 순서가 갑자기 바뀌는 것을 줄인다. 도착순 정렬 여부는 후속 결정이다.
- 완료 기준: 데이터 0개·1개·여러 개와 오류 상황을 모두 표시한다.

### FR-04: 관심 버스 선택

- 입력: 화면 선택 또는 물리 버튼 이벤트.
- 출력: 공용 관심 노선 ID와 선택 표시.
- 규칙: 식별은 route_id 사용. 같은 번호 또는 방향 혼동을 피한다.
- 도착 정보가 없는 노선도 메타데이터가 있으면 선택 가능하다.
- 화면 조작과 버튼 조작은 동일한 공용 상태를 변경한다.
- 후보 이동·확정·해제의 정확한 조작 규칙은 추후 결정한다.
- 완료 기준: 선택·해제가 명확하고 데이터 갱신 후 선택이 유지된다.

### FR-05: 도착 임박 표시

- 입력: 공용 선택, 최신 스냅샷, 임박 기준.
- 초기 기준 추천: 120초 이하.
- 출력: 큰 글씨 상태와 LED 상태.
- 상태 제안: 미선택 / 도착 정보 없음 / 대기 / 도착 임박 / 정보 오류 / 장치 미연결.
- 숫자·아이콘·문구를 함께 사용한다. 빨강·초록만으로 상태를 구분하지 않는다.
- LED의 색상은 후속 시안에서 확정하며 빠른 반복 점멸은 피한다.
- API 예측값만으로 실제 도착을 확정하지 않는다.
- 완료 기준: 121초와 120초를 구별하고 미상값에서는 임박 알림을 만들지 않는다.

### FR-06~07: 소리 알림

- 입력: 최신 임박 판단, 알림 사용 여부, 기존 기록.
- 출력: 짧은 부저 알림 및 알림 기록.
- 자동 소리는 임박 조건을 만족한 도착 대상당 한 번을 기본 목표로 한다.
- LED는 표시 기능, 부저는 일회성 이벤트로 분리한다.
- 시간 예측이 기준 위아래로 흔들려도 같은 도착 대상의 부저를 반복하지 않는다.
- 첫 실행부터 임박 상태이거나 선택 직후 임박 상태일 때의 알림 정책은 미확정이다.
- 차량 ID가 없으면 중복 판단 신뢰도가 낮다. 순위만으로 동일 차량이라고 단정하지 않는다. 보수적인 노선별 시간 제한을 임시 적용할 경우 한계를 문서화한다.
- 완료 기준: 화면 새로고침·여러 접속자·동일 명령 재전송으로 부저가 추가 발생하지 않는다.

### FR-08: 큰 글씨

- 입력: 큰 글씨 설정, 관심 노선과 도착 정보.
- 출력: 노선명·예상 시간·저상 여부를 확대한 영역.
- 기준: 일반 텍스트 20px 이상, 주요 숫자 48px 이상을 PC 초기 디자인 목표로 하되 화면 거리·모바일 폭으로 조정한다.
- 숫자가 없을 때도 ‘정보 없음’ 등 상태 문구를 크게 표시한다.
- 화면 확대 200%에서 핵심 정보와 조작이 유지되는지 확인한다.
- 완료 기준: 설정 변화가 노선 선택을 해제하지 않으며 모바일에서 잘리지 않는다.

### FR-09: 저상버스 안내

- 입력: 도착 차량별 유형.
- 출력: ‘저상버스’, ‘일반버스’, ‘기타 차량’, ‘차량 유형 정보 없음’.
- 다음 도착 차량과 두 번째 차량의 유형을 분리한다.
- 해당 노선 전체가 저상버스라고 단정하지 않는다.
- 저상 표시는 API의 차량 유형 안내이며 실제 승차 지원을 보장하는 표현은 사용하지 않는다.
- 완료 기준: 미제공값이 일반버스로 표시되지 않는다.

### FR-10~11: 간편 안내 요청과 음성

- 입력: 안내 버튼 이벤트, 공용 선택, 최신 스냅샷.
- 출력: 화면 강조와 한국어 음성.
- 문장 예시: ‘12번 버스는 약 3분 후 도착 예정입니다. 저상버스입니다.’
- 미선택 예시: ‘관심 버스를 선택해 주세요.’
- 오류 예시: ‘현재 버스 정보를 갱신하지 못했습니다. 화면의 마지막 갱신 시간을 확인해 주세요.’
- 정보 없음과 조회 실패는 다른 문장을 사용한다.
- 한국어 음성 설치 여부를 실제 PC에서 확인한다. TTS 도구를 설치했다고 한국어 재생이 자동 보장되지는 않는다.
- 음성 작업은 화면·시리얼 통신을 멈추지 않도록 큐 또는 별도 작업자로 관리한다.
- 연타 시 음성을 무한히 쌓지 않도록 진행 중 요청 병합과 짧은 요청 제한을 추천한다.
- 완료 기준: 버튼 1회에 안내 1회, 새 요청이 밀려 오래된 정보를 읽지 않는다.

### FR-12~14: 모바일 페이지와 개인 선택

- 입력: QR 주소, 현재 스냅샷, 개인 세션 선택.
- 출력: 모바일 도착 정보와 개인 선택 표시.
- 공용 선택·PC 부저·PC 음성에는 영향이 없어야 한다.
- QR 없이도 주소를 입력할 수 있도록 짧은 안내 주소를 함께 표시한다.
- 초기 완성 기준은 같은 WiFi 접속이다. 외부 접속은 별도 배포 단계로 둔다.
- 페이지를 닫거나 휴대폰이 절전 상태인 경우 자동 안내를 보장하지 않는다.
- 브라우저 음성은 이용자가 ‘음성 사용’ 버튼을 눌러 허용한 뒤 실제 기기에서 확인한다.
- 완료 기준: 두 휴대폰에서 서로 다른 노선을 선택할 수 있다.

### FR-15: 시연 모드

- 정상 대기, 도착 임박, 저상버스, 일반버스, 정보 없음, 오류, 오래된 정보, 차량 교체 사례를 준비한다.
- 모든 화면에 ‘시연 데이터’라고 표시한다.
- 시연과 실제 모드는 외부 조회 어댑터만 바꾸고 화면·판단 모듈은 공통 사용한다.
- 실제 모드 전환 시 이전 시연 선택·알림 기록을 안전하게 초기화하는 정책을 정한다.

## 9. 공용 화면과 모바일 화면 설계

화면의 영역과 표시 항목만 정의하며, 클릭·버튼 조작의 순서는 추후 사용자 흐름에서 정한다.

| 영역 | 공용 안내판 | 휴대폰 |
| --- | --- | --- |
| 상단 | 정류소명·방향·갱신 시각 | 동일 |
| 상태 | 실시간/갱신 실패/시연, 장치 연결 | 데이터 상태; 장치 상태는 간소화 가능 |
| 노선 목록 | 노선·시간·남은 정류장·저상 여부 | 세로 카드 또는 간단한 목록 |
| 관심 버스 | 공용 관심 노선 크게 표시 | 개인 관심 노선 표시 |
| 안내 조작 | 큰 글씨, 안내 요청, 자동 알림 설정 | 큰 글씨, 개인 음성 사용 |
| 하단 | QR·접속 안내·정보 출처 | 정보 출처·주의 문구 |

문구 예시:

- ‘약 3분 후 도착 예정’
- ‘2개 정류장 전’
- ‘도착 임박’
- ‘저상버스’
- ‘현재 도착 정보가 없습니다’
- ‘정보 갱신 실패 · 마지막 성공 17:00:00’
- ‘선택한 버스 없음’

도착 시간이 실제 초 단위로 제공되지 않으면 임의의 초 단위 카운트다운을 보여주지 않는다. 좁은 모바일 화면에서는 표의 가로 스크롤보다 세로 카드 구성을 추천한다.

## 10. Python–Arduino 통신 계약

### 10.1 초기 USB 규격 제안

| 항목 | 추천 값 |
| --- | --- |
| 전송 | USB 시리얼 |
| 속도 | 115200 baud, 양쪽 일치 |
| 포맷 | 한 줄당 JSON 메시지 1개, 끝에 LF |
| 문자 | 명령·키는 ASCII; 화면용 한글은 PC에서 처리 |
| 최대 메시지 | 초기 512바이트 제한 제안 |
| 버전 | protocol_version: 1 |
| 명령 ID | 같은 재전송에 동일 ID 사용 |
| 이벤트 ID | Arduino 부팅 세션 + 순번 |

이 규격은 제안이며 현재 구현된 통신이 아니다. JSON 파서 사용 시 보드 호환성과 버퍼 용량을 확인한다.

### 10.2 메시지 예시

Python에서 LED 상태 설정:

```json
{"protocol_version":1,"type":"command","id":101,"name":"set_indicator","payload":{"state":"imminent"}}
```

Python에서 부저 알림 요청:

```json
{"protocol_version":1,"type":"command","id":102,"name":"beep","payload":{"pattern":"arrival"}}
```

Arduino의 버튼 이벤트:

```json
{"protocol_version":1,"type":"event","boot_id":"demo_boot_1","seq":18,"name":"button_pressed","payload":{"button":"guide"}}
```

Arduino의 명령 처리 결과:

```json
{"protocol_version":1,"type":"ack","id":102,"ok":true}
```

### 10.3 명령과 이벤트 목록

| 이름 | 방향 | 의미 |
| --- | --- | --- |
| set_indicator | Python→Arduino | LED 상태 변경; 여러 번 적용해도 일회성 소리 없음 |
| beep | Python→Arduino | 부저 패턴 실행 |
| set_mute | Python→Arduino | 자동 부저 무음 설정 |
| ping | Python→Arduino | 연결 확인 |
| ready | Arduino→Python | 부팅·프로토콜 버전 알림 |
| button_pressed | Arduino→Python | next/select/guide 입력 |
| ack | Arduino→Python | 명령 수신·검증 결과 |
| error | Arduino→Python | 알 수 없는 명령·잘못된 값 |

### 10.4 안정성 규칙

- Python은 ACK를 수신한 뒤 전달 성공으로 기록한다. ACK 의미는 ‘명령 수신·적용 요청 수락’으로 정의하고 소리 재생 완료와 혼동하지 않는다.
- 부저 명령 재전송 시 Arduino가 최근 명령 ID를 기억하여 중복 실행하지 않도록 한다.
- 같은 이벤트를 재수신하면 boot_id + seq로 중복 제거한다.
- 잘린 JSON·여러 메시지가 한 번에 들어오는 상황을 줄 단위 버퍼로 처리한다.
- 잘못된 입력은 장치를 정지시키지 않고 오류 처리한다.
- 연결이 복구되면 LED 현재 상태는 다시 맞추되 지난 부저 알림을 자동 재생하지 않는다.
- 시리얼 모니터와 Python이 동시에 포트를 열지 않도록 한다.
- 재연결이 보드를 초기화하는지 확인하고 ready 수신·기동 대기를 둔다.
- 초기 ACK 제한 1초·최대 재시도 2회는 실험값이며 실제 동작으로 조정한다.

## 13. 설정 및 상태 관리

### 13.1 초기 설정값 제안

| 설정 | 초기 값 | 설명 |
| --- | --- | --- |
| DATA_MODE | demo 또는 live | 화면에 명확히 표시 |
| API_PROVIDER | 미정 | 정류소 결정 후 선택 |
| STATION_ID | 미정 | 비어 있으면 live 실행 오류 |
| API_SERVICE_KEY | 비밀 환경변수 | 코드에 직접 적지 않음 |
| POLL_INTERVAL_SECONDS | 30 | 호출 한도 확인 후 조정 |
| STALE_AFTER_SECONDS | 90 | 최신성 제한 |
| IMMINENT_THRESHOLD_SECONDS | 120 | 임박 기준 |
| SERIAL_PORT | 실제 COM 번호 | PC별 설정 |
| SERIAL_BAUD | 115200 | 보드와 일치 |
| AUDIO_ENABLED | true | 자동 알림 설정 |
| LED_BRIGHTNESS | 낮은 값으로 시작 | 부품 전류·시인성 확인 |
| MOBILE_BASE_URL | 접속 주소 확정 후 입력 | QR와 동일 |

### 13.2 상태 소유권

- 공용 상태는 서비스가 소유한다. Streamlit 세션은 복사본만 표시한다.
- 개인 상태는 모바일 세션에 둔다.
- 서비스 내부의 공유 캐시는 갱신 중 불완전한 값이 노출되지 않도록 스냅샷 교체 방식으로 관리한다.
- 여러 작업자가 같은 선택·알림 기록을 변경한다면 Lock 또는 단일 이벤트 큐로 보호한다. 스레드 구성 전까지 특정 Lock 사용을 필수라고 단정하지 않는다.
- 초기에는 메모리 상태로 충분하다. 장기 기록·통계가 필요해지면 SQLite를 별도 확장한다.
- 재시작 후 알림 기록 복원 여부는 미확정이다. 복원하지 않으면 재시작 직후 중복 알림 가능성을 시연에서 확인한다.

## 14. 오류·복구·로그 설계

| 상황 | 사용자 표시 | 시스템 기준 |
| --- | --- | --- |
| 인증키 없음·승인 문제 | 정보 서비스 설정 오류 | 반복 요청을 제한하고 개발자 로그 기록 |
| HTTP timeout | 정보 갱신 실패 | 제한된 재시도·다음 주기 복구 |
| 호출 한도 초과 | 정보 갱신 지연 | 조회 간격 확대·무한 재시도 금지 |
| 정상 응답에 결과 없음 | 도착 정보 없음 | 이전 차량 정보로 새 알림 금지 |
| 일부 필드 누락 | 해당 항목 정보 없음 | 다른 유효 항목 표시 유지 |
| 오래된 스냅샷 | 마지막 정보·갱신 지연 | 새 자동 알림 금지 |
| Arduino 분리 | 장치 미연결 | 화면 조회 유지·연결 복구 시도 |
| ACK 미수신 | 장치 응답 없음 | 명령별 제한 재시도 |
| 한국어 음성 없음 | 음성 안내 사용 불가 | 텍스트 안내 유지·설치 확인 |
| 서비스 접근 실패 | 서비스 연결 확인 필요 | UI 오류 상태, 비밀 없는 메시지 |

로그는 시각·심각도·모듈·이벤트·결과를 기록한다. API 키가 들어 있는 전체 요청 URL은 그대로 기록하지 않는다. 원본 차량 식별 정보는 중복 판단에 필요한 범위로 사용하고 기본 화면에는 표시하지 않는다. 로그 파일은 크기 제한과 순환 보관을 추천한다.

연결 복구와 업무 알림을 구분한다. 장치가 다시 연결되었다고 과거 임박 알림을 소리로 재생하지 않는다. 최신성은 마지막 성공 시각으로 판단하되 최근 실패 여부도 동시에 표시한다.

## 15. 접근성 및 사용성 기준

| 대상·상황 | 반영할 설계 |
| --- | --- |
| 시력이 낮은 이용자 | 큰 글씨·명확한 대비·음성 안내 |
| 청각 정보를 듣기 어려운 이용자 | 소리와 동일한 상태를 글자·LED로 제공 |
| 색상 구분이 어려운 이용자 | 상태 문구와 아이콘 병행 |
| 작은 터치 조작이 어려운 이용자 | 큰 버튼과 충분한 간격 |
| 휠체어 이용자 | 모형 버튼 위치·조작 도달성 고려, 차량별 저상 표시 |
| 휴대폰 조작이 익숙하지 않은 이용자 | 회원가입 없이 정보 제공, QR 옆 간단한 설명 |

- 웹 조작 요소는 44×44 CSS px 이상을 초기 목표로 한다.
- 키보드로 조작 가능한 기본 버튼과 명확한 포커스 표시를 사용한다.
- 아이콘만 있는 버튼보다 ‘안내 듣기’, ‘알림 끄기’처럼 이름을 제공한다.
- 글자가 많으면 핵심 숫자와 부가 정보를 구분한다.
- 음성은 과도하게 길지 않게 하고 노선명·예상 시간·저상 여부 중심으로 구성한다.
- PC 음성 자동 재생보다 요청형 안내를 우선한다.
- 빠른 점멸과 계속 울리는 부저는 피한다.
- 본 문서는 접근성 인증 기준 충족을 검증한 문서는 아니다. 실제 이용자 피드백과 기기 시험으로 개선한다.
